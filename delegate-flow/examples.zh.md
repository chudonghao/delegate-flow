# Delegate Flow 示例

## 需求澄清问题

写 design 文件前，强模型一次只问一个关键问题：

```text
在写设计文件前，我需要先确认一个关键点：

[一个具体问题]

可选：
A. [选项 A]
B. [选项 B]
C. [选项 C]

你倾向哪一个？如果都不合适，也可以直接描述你的想法。
```

## 方案比较与方向确认

需求和上下文基本清楚后，强模型先给方案，不直接写 design 文件：

```text
基于当前需求和项目上下文，我看到 3 个可行方案：

推荐方案：A. [方案名]
- 做法：[一句话]
- 优点：[一句话]
- 代价：[一句话]
- 推荐理由：[一句话]

备选方案：B. [方案名]
- 做法：[一句话]
- 优点：[一句话]
- 代价：[一句话]

备选方案：C. [方案名]
- 做法：[一句话]
- 优点：[一句话]
- 代价：[一句话]

我的建议是采用 A。你确认这个方向后，我再写 design 文件。
```

## 任务过大时的拆分

如果需求包含多个独立子系统，先拆分，不直接写大 design：

```text
这个需求包含多个可以独立设计和实施的部分：

1. [子任务 A]
2. [子任务 B]
3. [子任务 C]

建议先处理：[推荐的第一个子任务]

原因：
- [原因 1]
- [原因 2]

你确认后，我会先为这个子任务写 design 文件。
```

## 设计文件模板

保存到 `docs/delegate-flow/specs/YYYY-MM-DD-<topic>-design.zh.md`：

```markdown
# [任务名] 设计

## 需求与成功标准

[用户要解决的问题，以及可判断完成的成功标准。]

## 非目标

- [明确不做什么。]

## 项目上下文

- [相关文件、现有模式或约束。]
- [影响设计的近期变更或已知风险。]

## 设计方案

- [核心方案。]
- [关键数据结构、算法、模块边界或接口决定。]

## 关键取舍

- [为什么选择这个方案。]
- [为什么没有选择其他方案。]
```

## 工作模型派发 Prompt

用户确认设计和实施边界后，派发工作模型时使用：

```text
你是负责边界清晰实施任务的工作模型。

派发此任务时使用的子 agent 模型必须与下方“工作模型”一致。

目标：
[用一句话描述要达成的结果。]

非目标：
- [明确不能修改什么。]
- [明确哪些功能或重构不在范围内。]

工作模型：
[模型名]

用户已批准的设计：
- [设计摘要]
- [关键取舍]

范围内文件或模块：
- [路径或模块]

范围外文件或模块：
- [路径或模块]

设计约束：
- [强模型已经决定的架构、API、数据结构或算法。]

- 除非这里明确列出，否则不要引入新依赖。

实施步骤：
1. [具体步骤]
2. [具体步骤]
3. [具体步骤]

验证命令：
- [精确命令]

验收标准：
- [可观察行为]
- [测试或 lint 预期]

遇到以下情况停止并汇报：
```

## 工作模型约束 Prompt

当实施必须严格限制范围时，把这段加入工作模型任务：

```text
严格遵守交接单。不要扩大范围，不要引入新架构，不要重写无关代码，不要做产品决策。

如果计划不完整或与代码库冲突，停止并汇报阻塞点，不要猜测。

你的职责是实施，不是重新设计。
```

## 返工 Prompt

当工作模型第一次结果需要修正时使用：

```text
基于你之前的工作继续，但只处理以下审核发现：

发现：
1. [具体问题]
2. [具体问题]

保持原始范围不变。不要重构无关代码。如果修复这些问题需要设计变更，停止并解释原因。

只汇报：
- 相比上次修改了什么
- 已运行验证
- 剩余风险
```

## 强模型审核清单

工作模型汇报完成后使用：

```text
审核重点：
- 工作模型状态是什么？DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED
- 实现是否符合已批准的设计？
- 工作模型是否保持在请求范围内？
- 是否查看了实际 diff，而不是只相信工作模型总结？
- 验证输出是否有证据支持完成声明？
- 公共接口、数据结构和算法是否可维护？
- 请求的验证命令是否运行，并且是否通过？
- 测试是否聚焦行为，并且有意义？
- 是否存在未处理的边界情况、迁移、权限、安全或兼容性风险？
- 返工是否适合继续委派，还是应由强模型接手？
```

## 工作模型状态处理

收到工作模型汇报后使用：

```text
状态处理：
- DONE：进入强模型独立审核。
- DONE_WITH_CONCERNS：先阅读疑虑；如果影响正确性、范围或可维护性，先处理疑虑再审核。
- NEEDS_CONTEXT：补充缺失上下文，重新派发同一任务。
- BLOCKED：不要无变化重试；选择补上下文、升级模型、拆小任务，或回到用户确认方向。
```

## 模型分工示例

```text
强模型：GPT-5.5
工作模型：Sonnet 4.6

强模型负责：
- 需求
- 架构
- 数据结构
- 算法
- 交接单
- 审核

工作模型负责：
- 边界清晰的实施
- 聚焦测试
- 局部 lint 或类型修复
- 实施汇报
```
