# Delegate Flow

`delegate-flow` 是一个小型 Cursor skill 源码项目，用来固化模型委派工作流。

它表达一条规则：

> 强模型负责高影响决策。工作模型负责边界清晰、可验证、可回滚的实现。强模型审核结果。

## 文件

- `SKILL.zh.md` - 中文源稿，方便维护和迭代。
- `SKILL.md` - 英文正式版，供 Cursor 和 agent 发现、加载。
- `examples.zh.md` - 中文 prompt 模板源稿。
- `examples.md` - 英文 prompt 模板正式版。

## 预期用途

当你希望更强模型（例如 GPT-5.5）负责需求、架构、数据结构、算法、实施交接和审核，同时让成本更低或能力更弱的模型（例如 Sonnet 4.6）负责边界清晰的编码任务时，使用这个 skill。

这个项目采用干净的 skill 源码目录结构，之后可以复制到个人或项目级 skill 位置。

## 推荐维护方式

中文文件作为源稿：

```text
SKILL.zh.md
README.zh.md
examples.zh.md
```

英文文件作为正式加载版本：

```text
SKILL.md
README.md
examples.md
```

如果需要维护双语版本，推荐流程：

1. 强模型编写或修改中文源稿。
2. 工作模型把中文源稿翻译成英文正式版。
3. 强模型审核英文版是否丢失约束、弱化语气或改变边界。

## 与需求设计流程的关系

这个 skill 保留一个通用的软件工程原则：先沟通需求，再让用户审核设计，最后才进入实施。

但它不强制每次都写长篇正式计划。对于多数委派任务，推荐使用轻量流程：

```text
上下文探索 -> 需求沟通 -> 写 design 文件 -> 摘要+路径请用户审核 -> 写 handoff 文件 -> 摘要+路径请用户审核 -> 工作模型实施 -> 强模型独立审核
```

这里的关键不是文档长度，而是不要让工作模型在实现中偷偷承担设计判断。强模型必须先理解项目上下文，把目标、非目标、范围、设计约束、验证命令、停止条件和验收标准交代清楚，并在关键边界上让用户看见。

为避免浪费 token，完整内容写入文件；聊天里只给摘要、文件路径和确认请求。用户审核的是文件，不是聊天里重复粘贴的一份副本。

工作模型完成后，强模型不能只相信汇报总结；需要独立查看实际改动和验证证据，再决定接受、返工、升级模型或回到用户确认。

## 审核文件结构

进入委派实施前，必须保存两个授权文件：

```text
docs/delegate-flow/
├── specs/
│   └── YYYY-MM-DD-<topic>-design.zh.md
└── plans/
    └── YYYY-MM-DD-<topic>-handoff.zh.md
```

- `specs/` 保存用户已批准的设计，也就是“用户批准了什么”。
- `plans/` 保存工作模型实施交接单，也就是“工作模型被授权做什么”。

没有 design 文件，不进入实施。没有 handoff 文件，不派发工作模型。

## 安装为个人 Cursor Skill

把正式版文件复制到个人 Cursor skills 目录：

```text
~/.cursor/skills/delegate-flow/
```

安装后的目录至少应包含：

```text
delegate-flow/
├── SKILL.md
└── examples.md
```

如果你希望保留双语维护稿，也可以同时复制 `*.zh.md` 文件。

## 典型工作流

1. 在委派编码任务给子 agent 时加载 `delegate-flow`。
2. 强模型先了解项目上下文，再澄清需求并提出设计。
3. 强模型保存 `docs/delegate-flow/specs/YYYY-MM-DD-<topic>-design.zh.md`。
4. 强模型在聊天里给设计摘要和路径，请用户审核文件。
5. 强模型保存 `docs/delegate-flow/plans/YYYY-MM-DD-<topic>-handoff.zh.md`，并先自检。
6. 强模型在聊天里给交接单摘要和路径，请用户审核文件。
7. 用户确认关键实施边界。
8. 工作模型带着明确边界实施，并用明确状态汇报。
9. 强模型独立审核实际改动和验证证据后再接受。

## 推荐模型分工

强模型负责：

- 需求
- 架构
- 数据结构
- 算法
- 公共接口
- 实施交接
- 最终审核

工作模型负责：

- 聚焦代码修改
- 聚焦测试
- 与本任务相关的类型、lint 和格式修复
- 实施汇报

一旦任务需要新的产品或架构判断，工作模型应该停止并汇报。
