# Delegate Flow

## 核心原则

把最强的可用模型用于高影响决策，把成本更低或能力更弱的模型只用于边界清晰、可验证、可回滚的执行。

强模型：判断。工作模型：实施。强模型：验收。

## 何时使用

在以下情况使用这个 skill：

- 更强的父 agent 要把实现工作委派给子 agent。
- 模型成本很重要，但可维护性仍然更重要。
- 任务包含架构、数据结构、算法或模块边界决策。
- 工作模型具备编码能力，但不应该承担产品或架构判断。

不要用于非常简单的单步修改；如果委派带来的协调成本高于收益，就直接完成。

## 必须遵守的流程

1. 强模型先了解项目上下文，包括相关文件、现有模式、约束和近期变更。
2. 强模型澄清需求和成功标准。
3. 强模型判断任务范围是否过大；如果包含多个独立子系统，先和用户拆分。
4. 强模型提出 2-3 个可行方案，说明取舍，并给出推荐方案。
5. 用户确认推荐方向；如果用户不同意，强模型继续沟通方案，不写 design 文件。
6. 强模型把完整设计写入 `docs/delegate-flow/specs/YYYY-MM-DD-<topic>-design.zh.md`。
7. 强模型在对话中只提供设计摘要、文件路径和审核请求，不重复贴出完整设计。
8. 用户审核并批准设计；如果用户不同意，强模型先修正设计文件。
9. 强模型把完整短实施计划或实施交接单写入 `docs/delegate-flow/plans/YYYY-MM-DD-<topic>-handoff.zh.md`。
10. 强模型确认 handoff 已指定工作模型；如果未指定，先基于当前可用模型列表询问用户；如果拿不到可用模型列表，则向用户请求可选工作模型，不得编造，并把最终选择写入 handoff。
11. 强模型自检交接单，确认范围、验证命令、停止条件、验收标准和工作模型指定没有遗漏或模糊。
12. 强模型在对话中只提供交接单摘要、文件路径和审核请求，不重复贴出完整交接单。
13. 用户审核关键实施边界；如果边界不清楚，强模型先修正交接单文件。
14. 工作模型只在交接单边界内实施。
15. 工作模型汇报状态、修改文件、验证结果、失败项和残余风险。
16. 强模型独立审核实际改动、验证证据、架构适配性和范围控制。
17. 如果需要返工，强模型发送有边界的后续指令，不让工作模型重新设计。

## 用户审核 Gate

先沟通需求，再让用户审核设计和实施边界。

这个 skill 不要求每次都写长篇正式计划，但必须保留三个轻量 gate：

1. **方向确认**：写 design 文件前，用户确认推荐方案和关键取舍。
2. **设计确认**：用户审核 design 文件，确认目标、非目标、方案取舍和关键设计约束。
3. **实施边界确认**：用户审核 handoff 文件，确认范围、验证命令、停止条件和验收标准。

如果任务非常小，design 和 handoff 可以非常简短，但仍必须分别保存为文件，并由用户确认后，才能委派工作模型。

完整审核对象是文件。对话只提供摘要、路径和确认请求，避免把完整内容在聊天和文件中重复输出。

不要把“用户已经同意大方向”理解为“用户同意所有实施细节”。实施路径会影响可维护性，所以至少要让用户审核设计文件和交接单文件。

## Design 前沟通

写 design 文件前，强模型必须先完成需求和方案沟通：

- 先了解项目上下文，再提设计方向。
- 一次只问一个关键问题，避免把多个决策混在一起。
- 澄清目标、非目标、约束和成功标准。
- 判断任务是否过大；如果包含多个独立子系统，先拆成更小的设计任务。
- 提出 2-3 个可行方案，说明各自取舍。
- 给出推荐方案，并说明为什么推荐它。
- 等用户确认推荐方向后，才写 design 文件。

## 落盘规则

对话用于沟通，文件用于授权和追踪。完整内容写入文件，聊天只做摘要、路径和确认。

凡是进入委派实施的任务，必须保存两个文件：

- `docs/delegate-flow/specs/YYYY-MM-DD-<topic>-design.zh.md`：保存用户已批准的设计。
- `docs/delegate-flow/plans/YYYY-MM-DD-<topic>-handoff.zh.md`：保存用户已批准的工作模型交接单。

没有 design 文件，不进入实施。没有 handoff 文件，不派发工作模型。没有工作模型指定，不派发工作模型。

这两个文件只记录授权依据：用户批准了什么，以及工作模型被授权做什么。工作模型汇报和强模型审核可以留在对话中，不作为此 skill 的强制落盘要求。

## 强模型职责

强模型负责：

- 探索项目上下文和现有模式
- 需求和非目标
- 范围判断和任务拆分
- 方案比较和推荐
- 架构和模块边界
- 数据结构和算法
- 公共接口和持久化格式
- 风险评估
- 测试策略
- 交接单自检
- 确认 handoff 中的工作模型指定
- 保存并维护设计文件和交接单文件
- 最终审核和验收

强模型不能把模糊的设计工作交给能力更弱的工作模型。

## 工作模型指定

派发前必须确定工作模型。

- handoff 中必须写明最终使用的工作模型。
- 如果 handoff 未指定工作模型，强模型必须先依据当前平台暴露的可用模型列表询问用户，不得自行猜测。
- 如果当前环境没有暴露可用模型列表，强模型必须向用户请求可选工作模型，不得编造模型列表。
- 如果用户指定的模型不可用，强模型必须在对话中说明，并让用户从可用模型中重新选择。
- 实际派发子 agent 时使用的模型必须与 handoff 中记录的工作模型一致。
- 如果当前平台不支持指定 handoff 中的工作模型，强模型必须停止并询问用户，不得改用其他模型。
- 模型选择过程留在对话中；handoff 只记录最终工作模型。

handoff 中只需记录：

```text
工作模型：
```

## 交接单自检

把短实施计划或交接单给用户审核前，强模型先检查：

- 是否存在“适当处理”“补充测试”“优化一下”等模糊指令？
- 范围内和范围外文件或模块是否明确？
- 设计约束是否足够让工作模型不需要重新设计？
- 工作模型是否已经明确指定？
- 验证命令是否具体，并说明预期结果？
- 停止条件是否覆盖架构、数据模型、权限、安全、迁移和大范围重构？
- 验收标准是否能被客观判断？
- 多任务是否需要拆成独立小任务，而不是一次交给同一个工作模型？

## 工作模型边界

工作模型可以：

- 实施已经确定的计划
- 添加交接单要求的聚焦测试
- 遵循现有局部代码模式
- 修复由本次改动引入的 lint、类型和格式问题
- 清晰汇报阻塞点

工作模型必须用以下状态之一汇报：

- `DONE`：任务完成，验证已运行，可以进入强模型审核。
- `DONE_WITH_CONCERNS`：任务完成，但存在疑虑或残余风险，强模型必须先阅读疑虑再决定下一步。
- `NEEDS_CONTEXT`：缺少必要上下文，强模型补充信息后再派发。
- `BLOCKED`：任务无法继续，强模型判断是补上下文、升级模型、拆小任务，还是回到用户确认。

遇到以下情况，工作模型必须停止并汇报，而不是自行决定：

- 计划与现有代码冲突
- 需要判断公共 API、数据模型、迁移、安全规则或权限模型
- 测试因为分配范围之外的原因失败
- 实现需要大范围重构
- 工作模型想引入新架构、新依赖或新抽象

## 实施交接单

派发工作模型前，提供：

```text
目标：
非目标：
用户已批准的设计：
工作模型：
范围内文件或模块：
范围外文件或模块：
设计约束：
实施步骤：
验证命令：
验收标准：
遇到以下情况停止并汇报：
最终汇报格式：
```

交接单可以短，但每个边界必须明确。除非用户明确要求跳过，否则强模型应该在派发工作模型前让用户审核这份交接单。

## 处理工作模型状态

强模型收到工作模型汇报后：

- `DONE`：进入独立审核。
- `DONE_WITH_CONCERNS`：先判断疑虑是否影响正确性、范围或可维护性；如果影响，先处理疑虑再审核。
- `NEEDS_CONTEXT`：补充缺失上下文，重新派发同一任务。
- `BLOCKED`：不要强迫同一模型无变化重试；根据原因选择补上下文、升级到更强模型、拆小任务，或请用户重新确认方向。

## 审核清单

工作模型汇报后，强模型检查：

- 实现是否符合已批准的设计？
- 工作模型是否保持在请求范围内？
- 强模型是否查看了实际 diff，而不是只相信工作模型总结？
- 验证输出是否有证据支持完成声明？
- 数据结构、算法和公共接口是否仍然可维护？
- 请求的验证命令是否实际运行？
- 测试是否验证行为，而不是只验证实现细节？
- 是否留下未解决的迁移、权限、安全、兼容性或边界情况风险？
- 返工是否适合继续委派，还是应由强模型接手？

## 常见错误

| 错误 | 修正 |
| --- | --- |
| “工作模型可以自己补齐细节。” | 如果细节影响架构，强模型必须先决定。 |
| “我已经知道该怎么做，直接写 design。” | 写 design 前必须先完成需求/方案沟通，并让用户确认推荐方向。 |
| “只给一个方案最快。” | 强模型的价值在取舍；通常应给 2-3 个方案和推荐理由。 |
| “审核会抓住所有问题。” | 交接单先防止偏移，审核才更便宜。 |
| “编码是低风险工作。” | 核心状态、算法、权限和迁移即使表现为代码，本质仍是设计工作。 |
| “模糊 prompt 更省时间。” | 模糊委派会把决策权转移给工作流里能力最弱的一环。 |
| “用户批准了设计，所以可以直接派发。” | 设计批准不等于实施边界批准；至少给用户看短计划或交接单。 |
| “聊天里已经确认过了，不用保存。” | 进入委派实施前必须保存 design 和 handoff，文件才是授权依据。 |
| “文件里有了，聊天里再完整贴一遍。” | 完整内容只写文件；聊天只给摘要、路径和审核请求。 |
| “没指定工作模型也可以派发。” | 没有工作模型指定，不派发；先询问用户并写入 handoff。 |
| “工作模型说完成了。” | 强模型必须独立检查实际改动和验证证据。 |
| “工作模型卡住了，再试一次。” | 如果没有补上下文、换模型或拆任务，重复尝试通常只会重复失败。 |
